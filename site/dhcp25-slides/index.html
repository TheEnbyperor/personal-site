How these protocols work

All over ISO 7816-4, lots of BER TLV, some NDEF

Common start

SELECT OSE.VAS.01

  • 6F - File Control Information
    • 50 - Implementation
      • ApplePay or
      • AndroidPay
    • And that's all that's common between them...

Apple's Protocol

  • Phone gives its protocol version
  • Some other bits that can be safely ignored
  • GET DATA command with the SHA-256 hash of the pass type ID
  • Response has:
    • Pass public key fingerprint (4 bytes)
    • Device ephemeral public key (32 bytes)
    • AES-GCM encrypted data, containing:
      • Device timestamp (4 bytes)
      • Pass payload
  • Encryption key derived with ECDH and the X963 KDF
  • Payload decryption can happen after the fact,
    not even on the terminal
  • Not much more to it!

Google's Protocol

  • Phone gives protocol version(s) it supports
  • Also, device nonce and device ephemeral key
  • At this point, the protocol switches to NDEF from BER TLV
  • Terminal sends nonce and ephemeral public key
  • Terminal authenticated with signature over:
    • Terminal nonce
    • Device nonce
    • Merchant ID
    • Terminal ephemeral public key
  • Sequence number in all exchanges,
    to catch someone injecting commands in between
  • GET SMART TAP DATA command, with the type of pass wanted
    (e.g. event ticket, coupon, loyalty card)
  • Data returned AES-CTR encrypted
  • Encryption key generated using ECDH and the HKDF with SHA-256
  • Terminal authentication and payload decryption
    requires the merchant's global key to be on the terminal
